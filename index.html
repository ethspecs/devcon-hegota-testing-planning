bogota-devnet-1 and heze-devnet-1

What the first devnets taught us

Late spec changes

A consensus-breaking test release two days before launch. One EL client forked at the first keyed-nonce transaction.

RPC and tooling

Tracing and RPC endpoints failed on frame transactions in several clients. No spec tests cover them.

Config drift

Slot duration, blob schedule and IL deadline lived in five places that did not agree.

  • FOCIL has no censorship-resistance scenarios in assertoor or spamoor yet.
  • Fork-transition-only behaviour (8253) needs many devnets, not one.

Keep client names off the slide unless the bug is fixed and public. Details: the fork was at block 1788 on bogota-devnet-1, intrinsic gas missing the 12,100 keyed-nonce access cost from tests-bogota-devnet@v1.1.0.

Public client issues: go-ethereum#35783 (frame tx JSON-RPC drops frames, frameReceipts and payer), nethermind#14031 (public pool defaults to 300k validation gas, the spec limit is 100k). Spencer and Jochem on 8253: behaviour only at the fork transition, so test it on as many devnets as possible.

Must-haves

What do we need before Hegotá can ship?

Tools and interactions

  • Frames × FOCIL scenarios: ILs with frame txs, omission claims, censorship tests in assertoor / spamoor.
  • RPC and tracing spec tests for frame transactions.
  • Fork-transition tests on every devnet (8253).
  • What else is a MUST, and who owns it?

Mempool and DoS

  • Frame txs run arbitrary validation: do we need a mempool spec, or is per-client policy enough?
  • FOCIL makes the mempool consensus-adjacent: IL contents depend on what each EL accepts.
  • How do we test DoS resilience: validation gas limits, spam on devnets?

Known divergence already: nethermind#14031, public pool defaults to 300k validation gas against a 100k spec limit. That is the argument for a written mempool spec.

Devnet schedule

ACD decides, or the testing team decides?

Align on ACD
  • Every team commits on the call.
  • Slow: a devnet waits up to a week for a call slot.
  • Scope creep negotiated live.
Testing team decides
  • Fast: launch when N clients pass the test release.
  • ACD sets priority order, testing sets dates.
  • Risk: teams feel scheduled at, not consulted.

Middle ground: ACD agrees scope via a meta EIP PR, testing owns the launch date.

Lesson from Glamsterdam

One of the mistakes we made on our side on the EL was underestimating the complexity of 8037. The idea would be to include the more complex EIPs a lot earlier in the cycle.
Spencer, ACDT #97, 21 September 2026
  • Test the hardest interactions first: frames × FOCIL.
  • Then the complex single EIPs. Simple EIPs ride along later.

Source: ACDT #97 transcript, t=2092. The EELS tracker (#3664) states the same principle: "aiming to test the most complex EIPs first: frames x FOCIL interactions, then the more complex single EIPs."

Capacity

Fewer streams, or more in parallel?

Fewer streams
  • One merged devnet, everyone on the same thing.
  • Deep review of each EIP.
  • Slow: complex EIPs queue behind each other.
More in parallel
  • Feature devnets per lane (heze, bogota).
  • Faster coverage of the CFI list.
  • Thin review: flaws found late, at merge time.
  • What would best let your team do this: headcount, clearer priorities, fewer spec changes?
  • “No one looked at it”: named reviewer per EIP from each client team before devnet inclusion?

A development fork for execution-specs · 1 of 3

Today: one branch per EIP, devnets by hand

  • A devnet is a branch: the 8141 tip, 8250 fast-forwarded, 8272 and 7906 cherry-picked. The update workflow fails on the 8250 and 8272 collision, so every rebuild is manual.
  • Every change to 8141 rebases 8250, 8272 and 7906, each with its own force-push and lease bookkeeping.
  • A change spanning EIPs (#3824, #3825) has no home. On the devnet branch it is lost at the next rebuild, so it becomes stacked PRs.
  • Branches drift: the 8141 branch lagged forks/bogota by one fix, so its diff showed 29 files instead of its own 17.

Cost grows with EIPs × changes per EIP × devnets that include them.

Solid: branch base or fast-forward. Dashed: cherry-pick. Snapshot 14 Oct 2026.execution-specs#3824, #3825

This is the 14 October snapshot from the plan document. The point is not any one incident but that the cost is multiplicative.

Details if asked: update-devnet-branch works for devnets/heze/2 and devnets/focil/2, where the EIPs do not collide, and fails on bogota because 8250 and 8272 both insert a constants block at the same spot in frame_transaction.py. The 29-versus-17 drift was a modexp fix applied to ten older forks that eips/bogota/eip-8141 never picked up.

A development fork for execution-specs · 2 of 3

One source tree, devnets as targets

develop/eips.py: the control board 
EIP_8141 = True   # every flag on in develop/
EIP_8250 = True
REQUIRES = {8250: {8141}, 8272: {8141}, 7906: {8141}}
OWNED_MODULES = {8250: ("keyed_nonces",), ...}
TARGETS = {
  "bogota":         Target({8141}, generated=True),
  "bogota_devnet1": Target({8250, 8272, 7906}, base="bogota"),
}
In one sentence

Every CFI EIP lives in develop/ behind its flag, and the tooling generates the code for any fork from any combination of those EIPs.

A fork or devnet is a name and an EIP set. The fold produces it; nobody assembles it.

Pilot: four EIPs guarded, Bogota generated, the devnet filled as a pseudo-fork reproduces the branch fixtures, 652 of 652.

Demo here. Show eips.py, then vm/gas.py and transactions/frame_transaction.py, then move 8250 into Bogota, regenerate, and show the framework following with no edit.

The framework side is one line per fork: class Bogota(TargetEIPs("bogota"), Amsterdam) and class BogotaDevnet1(TargetEIPs("bogota_devnet1"), Bogota). A hand-edited generated folder fails --check. A devnet is a superset of its base, so every valid_from("Bogota") test collects at the pseudo-fork unchanged.

Pilot numbers: tests/bogota at BogotaDevnet1 against the devnet worktree at release tests-bogota-devnet@v1.1.1: 652 identical, 0 differ, 4 branch-only (8141's own transition fixtures). Bogota fill unchanged at 256.

Cost and open questions

Cost

  • The barrier for writing specs goes up. An EIP is written in develop/, under its semantics and guard rules, not as a free-standing edit of one fork.

Mitigation

  • Keep the semantics as close to today's pseudo-code-like specs as possible.
  • Additional documentation for developers and for AI tools.

Open

  • Do we fill every combination of EIPs in develop/?

Proposal

  • No. Only the targets named in eips.py, plus the full develop/ spec.

Open

  • What network name do clients see on a devnet fixture: BogotaDevnet1 or Bogota?

Proposal

  • The pseudo-fork name, BogotaDevnet1. Hive and client configs key on fork names. To confirm with the hive-tests side.

Smaller costs if asked: PRs carry generated output next to the source (one just recipe produces it, CI checks it reproduces); a generated fork can carry residue from a dropped EIP until someone cleans it up; every fill and CI target pays a fold of about ten seconds. The branch tooling stays until the migration is done.

Ask the room for a decision on the devnet network name, since hive and client configs key on it. Other open points, if raised: sibling generated forks versus copies for a second open fork, what removing an EIP from develop/ looks like, and conditional prose in shared docstrings.
